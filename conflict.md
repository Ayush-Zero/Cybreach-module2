### B6. `rule_id` type and derivation disagreed - Alpha never adopted the canonical id

- **Violates:** plan Section 8 tech-stack/db schema `detection_rules (rule_id, ...)`; the cross-pod traceability guarantee.
- **Where (closed in Delta):** Delta's verdict-side surface is string-keyed on the canonical content hash: `Rule.rule_id` is `String(64) unique` (`cybreach_pod_delta/backend/app/models/rule.py:14`), `Verdict.rule_id` is `String(64)` with a foreign key onto it (`app/models/verdict.py:43`), the response type is `str` (`app/schemas/verdict.py:13`), and both dashboard services declare `rule_id: string` (`frontend-dashboard/src/services/verdictService.ts:10`, `revalidationDashboardService.ts:8`). Both joins now agree: `app/services/causal_chain_service.py:24` and `app/services/dashboard_service.py:27` both join `Rule.rule_id == Verdict.rule_id`. `Rule.id` remains Delta's local surrogate key for its own `/rules` routes, which is correct - that is Delta's rule-management surface, not a cross-pod identity.
- **Where (now closed - all of it was Alpha):** Alpha now assigns the canonical content hash as `rule_id` on both the valid and invalid ingest paths (`app/api/rules.py`: `rule_id=h`, where `h` is the same SHA-256 written to `content_hash`), so every rule Alpha serves is keyed by the digest Beta and Delta compute. `rule_id` and `content_hash` are the same string on every ingested rule.
- **Impact:** Resolved: a rule produced by Alpha is keyed by the string Beta and Delta compute, so a rule ingested upstream can be traced to the verdict that Beta and Delta publish about it.
- **Resolution:** Freeze `rule_id` as the content-hash string in the shared schema; make Alpha assign the digest.
- **Status:** RESOLVED. Both pods conform; Alpha's ingest and error paths assign the digest, and the read-side API (filtering, search, versioning, deprecation) is unchanged because tests seed `INGESTED_RULES` directly (all 60 ingest/search/versioning/filtering tests pass).

## Priority Actions

1. **Rotate the two Delta credentials at the database** (m7) - the last item in the register that is not a code change, and the only part of m7 that actually reduces risk. The exposure is recorded in `cybreach_pod_delta/SECURITY_EXPOSURE.md`; the remote is public, so both values must be treated as compromised regardless of the fact they were development credentials. Update the deployment environment to match - `DATABASE_URL` is the single source of truth.
2. **Decide on the Delta history rewrite** (m7) - optional rather than required. It rewrites hashes for every collaborator and is irreversible for existing clones, and GitHub keeps unreachable objects reachable through cached views and forks until the credential is rotated, so rotation must happen either way. Left to the team.
3. **End-to-end evidence flow (B1)** - **DONE, verified live on 2026-10-01.** A sigma rule was ingested into Alpha, an evidence event was published to `cybreach.evidence.v1`, and Beta consumed it, fetched Alpha's rules over authenticated HTTP, matched the rule, and published `verdict=Detected confidence=0.9` to `cybreach.verdicts.v2` with a `content_hash` that re-derives from the eight frozen fields. Four defects surfaced only at runtime and are fixed (M4's unusable rules URL and missing token, Alpha's fatal gRPC import, Beta's coroutine consumer). Two things remain open from that run and both need a decision:
   - **One PostgreSQL, four Alembic version tables.** Every pod is pointed at the same database, so only one pod's migrations can ever run - Alpha's `alembic upgrade head` refuses with "Can't locate revision identified by `0001_initial_verdict_platform`", which is Delta's. Alpha was also writing to a `detection_rules` table predating B11, so ingest died on `column detection_rules.tenant_id does not exist`; `create_all()` creates missing tables but never adds columns to existing ones, and the SQLite default had hidden it. Worked around with a per-pod database for the run. The real fix is per-pod databases or per-pod `version_table` settings, which is a data-layout decision rather than a code change.
   - **The bus path has no per-producer identity.** Beta mints a service token from the shared `SECRET_KEY`, so anything able to publish to `cybreach.evidence.v1` is implicitly trusted to cause validation and publication as `B11_SERVICE_TENANT_ID`. Acceptable only while the topic is ACL-protected; per-producer attribution needs a signed envelope.
4. **Serve or drop the gRPC prototypes (M9)** - not inert, as this register previously recorded: an unguarded stub import in Alpha's startup hook made the whole REST service unbootable, which the live run hit immediately. That is fixed, but the two original problems stand - `add_insecure_port` would serve tenant-scoped reads with no JWT, and the servicers return fabricated results. If they are ever to be served they need a JWT interceptor and the real normalizer behind them; otherwise delete them rather than leave a second, ungated front door.
